# Operator tools

Scripts that drive tmux, the crontab and the host process table. They cannot be run from
the checkout, because the checkout is mid-merge for minutes at a time, so they are
**deployed** to `~/.cache/mipstarre-dev/owner-bin/` by one versioned installer and are
**never edited on the host**. The file in this directory is the source of truth; the copy
under `owner-bin/` is a build output with a recorded hash.

On 2026-09-12 the same scripts lived in `/tmp` under names that no longer described their
contents (`lane-v17.sh` was really v20), were patched in place by `assert anchor in src`
here-docs, and ran in three simultaneous versions. That is what the installer exists to
prevent.

## Install

```sh
results/telemetry/owner-tools/install.sh --compat-tmp --crons --start-loops
```

`--start-loops` is not optional in practice: it starts `capacityd.sh`, and without a
running controller nothing writes `watchdog/max-codex-*` again — no AIMD, no 5xx trip,
no half-open probe, and on a fresh host no cap files at all, which makes
`lane.sh:wait_for_slot` fail closed with `no-capacity-record`. The full run-start
sequence is in `local/protocols/full-speed-mode.md` §2.

| Flag | Effect |
|---|---|
| *(none)* | copy every tool into `owner-bin/`, write `tools-version`, `manifest.sha256`, `manifest.accepted` and `repo-root` |
| `--force` | overwrite a deployed copy whose hash matches no released version; the previous copy is **moved** to `owner-bin/attic/<ts>/`, never deleted |
| `--compat-tmp` | create `/tmp/<name>` **symlinks** into `owner-bin/` for every historical name the 2026-09-12 run used, so an old invocation runs versioned code. A regular file in `/tmp` is left alone, not clobbered |
| `--crons` | run `install-crons.sh` afterwards |
| `--start-loops` | start `capacityd.sh` (the 60 s capacity controller) unless it is already running or `watchdog/capacity/capacityd.stop` holds it. The merge daemon and the keeper are not started here — `owner-resume.sh` owns those |
| `--dry-run` | print the plan; touch nothing |
| `--verify` | check every deployed file against `manifest.sha256`; exit 3 on a missing file or a mismatch. This is the merge daemon's start-up gate |
| `--record <name>` | re-record one regenerated file's hash (`run_mode.py set speed` calls it for `codex`), accepted only if the new hash is an `manifest.accepted` variant |

**The refusal rule.** A deployed file whose hash is neither the incoming one, nor the
manifest row, nor an accepted variant, nor a hash in an attic manifest is a hand patch: the
install stops with exit 4 and names the file. `--force` is the only way past and keeps the
patch in the attic. This is what makes "never edited on the host" checkable rather than a
convention.

**Version stamping.** Every installed tool prints `tool=<name> version=<sha>` as its first
log line, where `<sha>` is `short=` from `owner-bin/tools-version`. Lane markers
(`.done` / `.needs-attention`) carry the same string, so a lane log names the code that
produced it, and the daemon's marker-clearing rule can key on "the installed tools-version
is newer than the marker". The PATH shim is the one exception: its stdout is the worker's
stream, so it prints nothing.

## The owner's five commands

```sh
owner-bin/owner-pause.sh  [--deadline 15m] [--reason "..."] [--dry-run]
owner-bin/owner-resume.sh [--dry-run] [--force-crontab]
owner-bin/owner-say.sh --mode idle|interrupt|terminal [--timeout N] "TEXT"
owner-bin/install-crons.sh [--paused] [--dry-run] [--restore FILE]
owner-bin/accounts.sh     list | get | set | enable | disable | add | remove | probe | log
```

### `accounts.sh` — the keys, their ceilings and their health

`~/.cache/mipstarre-dev/watchdog/accounts.json` is the **live** source of truth for
admission: one entry per key, `{name, label, endpoint, codex_home, ceiling,
external_reserved, enabled, note}`, any number of endpoints and keys. The capacity
controller and `account_router.py` re-read it every tick and every reservation, so an edit
reaches admission within 60 seconds with **no session prompted, no brief re-applied and
nothing restarted**. `run_mode.py apply` seeds the file from the brief when it is absent and
never overwrites an existing one.

```sh
accounts.sh list                                  # every key, its ceiling and its state
accounts.sh set second ceiling 20                 # the admin took slots back
accounts.sh set second reserved 4                 # a forked session shares this key
accounts.sh disable second --note "quota gone"    # cap 0 immediately, no probes
accounts.sh enable second
accounts.sh add third --endpoint api.third.example \
    --codex-home ~/.codex-third --ceiling 8       # routable at the next reservation
accounts.sh remove third
accounts.sh probe second                          # one read-only health probe, now
accounts.sh log -n 20                             # who changed what, and when
```

* **`ceiling` is a ceiling, never a target.** The controller's AIMD discovery runs below it
  and may never exceed `ceiling - external_reserved`. Lowering it takes effect at the next
  tick; raising it lets the additive creep continue — the cap does not leap to the new
  number. A run sitting at 60 % of the ceiling with no refusals is behaving correctly.
* **`external_reserved == ceiling` is legal** and means the key has no slot for the pipeline
  right now — an honest state during a run, and different from `enabled: false`, which is a
  decision.
* **No key value is ever stored.** An entry names the codex home the key lives in; the
  secret stays in that directory, which only the owner touches.
* Every write is atomic (temp file + rename) and appends one line to
  `watchdog/capacity/accounts.log`. A bad field is refused with the field named and the file
  is left byte-identical, so the controller reading it a millisecond later never sees a
  half-file.

**From GitHub, when there is no shell.** A comment on the owner inbox issue in the fixed
form `ACCOUNTS: <name> ceiling=<n> [reserved=<n>] [enabled=true|false]` (one or more lines
per comment) is applied by `local/bin/janitor.sh` at its next sweep and answered with one
reply saying exactly what took effect (`applied: second ceiling 30 -> 20`, or `rejected: …`
with the reason). Only comments written by the repository owner login recorded in
`local/README.md` are applied; anyone else's are answered with a `rejected:` line naming
them. The channel carries `ceiling`, `reserved`, `enabled` and `note` only — an endpoint or
a codex home is a path on the host and is set here, where a typo cannot travel through a
public comment.

**Measured health.** A key that answers `401`/`403`/invalid-key or `INSUFFICIENT_BALANCE`
disables itself at the first occurrence, and an endpoint answering 5xx three times in two
minutes does the same; both record the REASON in `watchdog/capacity/health.json` and cap the
key at 0. A disabled key probes its own way back (read-only, bounded, single-flight) and
returns at cap 1, never at its pre-outage cap. The hourly readiness report on the progress
issue carries one line per key — ceiling, effective cap, live, refusals in the last ten
minutes, health with its reason, and the owner's own note — so none of this needs a question
to a session.

### `owner-pause.sh` — pause within the deadline

The deadline comes from `run.pause_deadline_min` in the run brief; no timestamp is written
into the script. `--dry-run` prints the phase plan and the computed deadline and touches
nothing.

| T | Phase |
|---|---|
| +0:00 | `run_mode.py pause` — caps to 0, pre-pause caps saved **inside** `capacity/state.json`; `touch watchdog/drain` |
| +0:30 | queued dispatches release themselves at the drain (none is killed); keeper, merge daemon, stack-watch and **capacityd** stopped by stop file (**kept**) and by a pid the script verifies against `/proc/<pid>/cmdline` first — a paused pipeline has no daemons running, and on a 128-core host shared with other users a recycled pid is real |
| +1:00 | exactly one `owner-say.sh --mode terminal`: closing progress comment and handoff, no prose on the estimate issue, **no auto-resume** |
| +2:00 | `crontab -l` backed up verbatim to `$W/crontab.<ts>.bak` (the phase fails if it returns nothing), then the paused crontab installed from a file under `$W` |
| D−2:00 | leftovers killed with anchored patterns only, SIGTERM then SIGKILL after 20 s; partial work stays in the worker's worktree, never `git clean` |
| D−0:01 | "Goal paused" confirmed in the pane, `watchdog/pause-state.json` written, `stages.jsonl` and an `events.d/` entry appended, telemetry committed and published through `checked-push.sh`. One minute **before** the deadline, so a publish that takes a few seconds still finishes inside "within 15 minutes" |

`watchdog/pause-state.json` is the single record: caps (**from run-mode, not from the
already-zeroed live files**), speed, estimate cadence, crontab backup path and both
sha256s, daemon PAR, the whole run mode, the measured limits, the main goal state and
`paused_at`. It is written twice — a provisional copy (`status: pausing`) as soon as the
caps are known, so a pause that dies mid-way still leaves the one number the resume cannot
reconstruct, and the complete one (`status: paused`) after the telemetry is published, so
it also lists the phases that failed at the very end. A deadline shorter than the nominal
plan clamps the later phases onto it instead of running past it; the printed plan says so.

### `owner-resume.sh` — restore from that record only

`run_mode.py resume` for caps and speed; the crontab restored **verbatim** from the
recorded backup with no `sed` un-commenting (the 2026-09-12 script's
`sed -E 's#^\#PAUSED-2026[0-9]{4} ##'` would have resurrected the watchdog, astra-poll and
heartbeat rows that have been deliberately off since 2026-09-09); a refusal with a printed
diff when the live crontab is not the one the pause installed; **capacityd**, daemon,
stack-watch and keeper restarted and every stop file removed; one resume message rendered
from `run_mode.py show`. Then a post-condition check that fails loudly: every cap file
exists, is numeric and nonzero for an account the brief enables (queried as
`run_mode.py get enabled.<account>`, whose answer is `yes`/`no` — a briefed
`enabled: false` account is skipped, not reported as a failure), no account is `down`, a
capacity controller and a merge daemon are actually running, and `watchdog/drain` is gone.
A resume that leaves no controller running exits 5: its caps could never move again.

### `owner-say.sh` — one message, three modes

* `idle` — wait for idle, never interrupt a turn.
* `interrupt` — Escape after the grace, send, then `/goal resume`.
* `terminal` — write `watchdog/goal-hold` **first**, Escape, send, and do **not** resume.
  On 2026-09-12 the terminal stop order at 08:19Z was followed by an automatic goal resume
  at 08:24Z; `goal-hold` is what stops `goal-keeper.sh` from doing that.

Idleness is judged on the **last four non-empty lines** of the pane only. A stale
"esc to interrupt" line in the scrollback made the previous version wait 20 minutes
(2026-09-12 04:01Z–04:21Z).

### `goal-keeper.sh`

Two-minute tick: resume a stalled or paused goal, set the goal on a goal-less idle session,
Escape a turn longer than `turn_max_min` (8 minutes in fast mode), and **drain
`watchdog/main-inbox/`** so a dispatch nudge never waits for a long turn to end. The goal
text is rendered from `run_mode.py show --oneline`; no cap, issue number or turn limit is
written into the script. It does nothing at all while `watchdog/goal-hold` exists.

Inbox file format: one message per file, one line; an optional first line
`#mode: idle|interrupt|terminal` picks the delivery mode (default `interrupt`). Delivered
files move to `main-inbox/sent/`.

### `install-crons.sh`

Regenerates the managed block of the crontab from the run mode — the estimate row at
`estimate_cadence_min` (30 minutes in fast mode, 6 hours otherwise), the readiness report
hourly and a five-minute row that restarts `capacityd.sh` if it is not running (the loop
takes a lock, so the row can never create a second controller). The readiness and capacityd
schedules are fixed policy, not brief fields — there is no `cron.<name>` knob, and nothing
here reads one. The watchdog, heartbeat and astra-poll rows have been deliberately off since
2026-09-09 and are written as comments saying so. Every other line of the live crontab is
carried through verbatim, **including commented-out lines**: a `#PAUSED-…` row carries a
schedule someone will want back, and dropping it would leave that schedule only in a backup
file. It always backs up first (to
`$W/crontab.<ts>.install.bak`, a name distinct from the pause's own
`$W/crontab.<ts>.bak`, so an install a second later cannot overwrite the file
`pause-state.json` points at), always installs from a file under `$W`, never `sed`s the
live crontab, and **fails if `crontab -l` returns nothing** — which is what a wipe looks
like, and one happened on 2026-09-12 through a `#` delimiter inside an `s#…#…#` expression.
`--restore FILE` installs a file verbatim through the same guarded path; that is how
`owner-resume.sh` puts the pre-pause crontab back.

### `estimate.sh`

Cheap enough for a 30-minute cadence: open PRs come from the committed read-only
`results/telemetry/github-snapshot/open-pulls.json` instead of up to 100 `gh pr view` calls
(the in-PR count is labelled as snapshot-derived, with the snapshot's age), the branch diffs
run in a throwaway worktree under the cache root instead of dirtying the primary checkout's
`FETCH_HEAD` under `checked-push.sh`, the 24-hour-ago site count is cached for the clock
hour, the whole run is wrapped in `timeout`, and the body is rendered by
`local/bin/estimate_post.py`, the single writer of the estimate issue. The denominator
stays 197 and the `<sub>` provenance line stays, so `estimates.jsonl` remains comparable
across the whole series.

### `owner-bin-codex` — the PATH shim template

The deployed `owner-bin/codex` is **generated** from this template. `run_mode.py set speed
fast|default` rewrites the single `@speed-args@` line to add or drop
`-c 'service_tier="priority"'` and then calls `install.sh --record codex`; both renderings
are recorded in `manifest.accepted`, which is why the regenerated file is not mistaken for a
hand patch. This replaces the 2026-09-12 `speed-fast.sh` / `speed-default.sh` string
surgery, which asserted an exact 90-character substring of a generated file.

The shim does **not** rewrite the model. The `gpt-5.6-sol → gpt-6-astra` rewrite it used to
carry made `sessions.jsonl` record a model that never ran; a run-wide override belongs in
`models.override` in the run brief, where telemetry can see it.

`models.override` resolves from the speed tier: **in full speed mode every role, reviewers
included, runs the hard model**, so `null` means `astra-all` whenever `run.speed` is `fast`
and the published `local/model-policy.json` otherwise. Write `"policy"` to keep the
published policy during a fast run, `"astra-all"` to force the hard model at default speed.
`run_mode.py set speed` re-resolves the field and rewrites `watchdog/model-override` with
it, and then regenerates the crontab through `install-crons.sh` — the estimate cadence
lives there, and a tier switch that leaves it alone is half a switch. `run_mode.py get
model_override` answers with what is in force; `model_override_source` says why.

## Launching the main session

`local/bin/main-session.sh` is the only launcher. It reads the model, the effort and the
`CODEX_HOME` from the brief's `run.main` block (`run_mode.py get main.model`,
`main.effort`, `main.codex_home`) and the tier from `run_mode.py get speed`, and invokes
codex **through the shim path**. When the run mode is unreadable it falls back to
`gpt-6-astra` / `xhigh` / the ambient `CODEX_HOME` and says `source: defaults` on its
banner, so a silent fallback is never mistaken for a briefed value. `launch_qpbt_main.sh` is a retirement stub that points at it and starts nothing;
`main-session-astra-v3.sh` (which lived only in `/tmp`) is gone.
