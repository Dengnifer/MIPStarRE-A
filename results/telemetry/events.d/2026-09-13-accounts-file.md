# Incident and observation log — shard

One session's dated bullets.  `results/telemetry/events.md` holds the history
before sharding; `telemetry.py events --since DATE` reads both.

## 2026-09-13

- **The set of usable keys was a message, and two of them were hard-coded (W10).** Symptom: the owner has one to three endpoints, each with one or two API keys, and each key's concurrency limit moves during a run — the endpoint's admin reassigns slots, the owner wins them back, a key becomes invalid, a key runs out of quota. On 2026-09-12 every one of those events reached the pipeline as a prompt to the meta session, which had to be idle to receive it, and the caps were then edited by hand ten times. W1 fixed the start of a run (one brief, one mode file) but not its middle: the brief is one-shot, changing a ceiling meant re-applying it and re-seeding every derived value, and nothing at all let the owner add or retire a key. Two names were hard-coded through the layer — `account_router.ACCOUNTS = ("primary", "second")`, `run_mode.ACCOUNT_NAMES`, `dispatch.sh`'s `for account in primary second`, the `--account` choices, the second key's `CODEX_HOME` as a special case — so a third key could not be expressed. Diagnosis: the thing that changes most often during a run was the only thing with no live file; and a two-element tuple had become a schema. Fix: `~/.cache/mipstarre-dev/watchdog/accounts.json` is the owner's live source of truth — one entry per key, `{name, label, endpoint, codex_home, ceiling, external_reserved, enabled, note}`, no key value ever stored in it — seeded once by `run_mode.py apply` and never overwritten by it; `local/bin/accounts_file.py` owns its schema, its atomic writes, its `accounts.log` audit line and the `ACCOUNTS:` directive grammar; the capacity controller and `account_router.py` re-read it every tick and every reservation, so a lowered ceiling is in force within 60 s and a disabled or removed entry is cap 0 with no probe; `results/telemetry/owner-tools/accounts.sh` is the owner's command and `local/bin/accounts_inbox.py` (a sixth janitor pass) applies `ACCOUNTS: <name> ceiling=<n>` comments on the owner inbox from the repository owner's login only, echoing back `applied:` / `rejected:` per line. Lesson: whatever the owner has to restate during a run is the thing that needed a file, and a closed set of names written into five call sites is a schema nobody agreed to.
- **A key that does not work is not a key that is busy.** Symptom: an invalid key and an exhausted balance were indistinguishable from a concurrency refusal, so the AIMD walked the cap down a quarter at a time while every session on that key died, and "cap 0" carried no reason a person could read without opening captures. Diagnosis: the health machine had exactly one trip condition (three 5xx in two minutes) and no vocabulary for "this key itself is refused". Fix: `local/capacity-policy.json` marks `auth` and `insufficient_balance` with `"disables": true` and gains `disable_threshold` (1) and `disable_backoff_s` (300); one such failure takes the key to cap 0 immediately with the reason recorded, the way back is the same half-open read-only probe restoring cap 1, and `watchdog/capacity/health.json` carries one row per key — state, reason, `disabled_by`, next probe — which `capacity_controller.py status`, `accounts.sh` and the hourly per-key line on the progress issue all quote. Lesson: a `401` is not a statistic; a threshold that treats it as one spends a hundred sessions proving what the first response already said.
- **The owner's per-key picture lived on the host.** Symptom: the state of a key — its ceiling, the cap actually in force, how many workers were on it, whether it was refusing — could only be read by running `capacity_controller.py status` on ghz, so it reached the owner as prose from a session. Fix: `local/bin/ready_report.py` adds one line per key to the hourly comment on the progress issue: ceiling, effective cap, live, refusals in the last ten minutes, health with its reason, and the owner's own `note` echoed back; the same rows go to `merge-latency-<date>.jsonl`, and a key's ceiling, cap, health or enabled flag changing joins the suppression signature so the next hour's comment is posted rather than suppressed. Lesson: a number the owner has to ask for is a number that belongs in the channel they already read.
