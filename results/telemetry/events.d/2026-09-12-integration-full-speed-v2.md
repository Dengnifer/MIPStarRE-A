## 2026-09-12

- **Capacity, the estimate channel and the speed tier had no single source (W1).** Symptom: during the full speed run the owner restated the two keys' limits several times and the operator edited `watchdog/max-codex-*` by hand ten times (39 -> 29 -> 20 -> 18 -> 14 -> 12 -> 6 -> 14 -> 22 -> 0); the resume script still announced "primary 5 / second 39 / total 44" after those numbers were wrong, and its cap restore would have written empty cap files, after which `account_router.py` exits 4 with `invalid literal for int()`. Multi-line progress reports appeared on the estimate issue and one had to be reformatted by hand, while a missing `watchdog/estimate-issue` made the cron post nothing at all, silently. The speed tier was switched three times by patching the deployed PATH shim with an `assert old in s` against a 90-character substring, and the main TUI never received the tier because its launcher exec'd an absolute codex path. Diagnosis: every number the owner stated lived in several places at once - a message, a cap file, a goal text, a script literal - and no component had one accessor for it; the estimate issue had no single writer; the shim had no committed source of truth. Fix: `local/bin/run_mode.py` validates one briefing into `watchdog/run-mode.json`, derives the cap files (never empty, never non-numeric, an unreadable one being unknown rather than zero), regenerates the shim from the committed template and refuses a hand-edited one with a diff; `estimate_post.py` renders the two-line estimate and refuses any other body; `ready_report.py` posts the hourly readiness report with each ready-but-open PR's reason read from daemon state; `full-speed-mode.md`, `main.md` (Standing reports) and `issues-prs.md` 6.1 carry the rules, and the retired inbox #26 is swept to #500. Lesson: a number the owner states once must have exactly one home and exactly one accessor - a second copy is wrong within the hour, and a channel with more than one writer drifts back to prose.
- **Nothing measured the limit and nothing noticed the dead endpoint (W3).** Symptom: 69 sessions died in an hour against a primary endpoint that had been answering 503 the whole time, and the rest died above the second key's real concurrency limit; the caps were chased by hand through ten values and the pause/resume round trip saved zeros it could not parse back. Diagnosis: the caps were operator opinion written into three files, with no measurement underneath them and no per-endpoint health at all, so every correction was a guess made after the deaths. Fix: `local/bin/capacity_controller.py` is the only writer of the cap files - additive increase after a full quiet window at saturation, multiplicative decrease on the first refusal of a window, per-endpoint attribution from the structured `failure_class`/`endpoint` fields, three `endpoint_5xx` deaths inside 120 s tripping the account to cap 0, recovery through a single half-open read-only probe, and the measured limit carried into the next run's seed. Lesson: a ceiling the owner states is a ceiling, never a target; the number that matters has to be measured, and an endpoint with no health check is an endpoint that fails silently for an hour.
- **The operator layer lived in /tmp and disagreed with itself (W4).** Symptom: four pause variants, two owner-say revisions, two launchers and two estimate copies existed only in `/tmp` and `~/bin`; one pause script had wiped the crontab with a `sed` delimiter bug; the speed switch asserted an exact 90-character substring of a generated file; and the goal keeper resumed the goal five minutes after the owner's terminal stop order. Diagnosis: there was no deployment step, so every fix was a copy and every copy was a fork, and the message channel had no way to express "this message does not resume". Fix: one versioned `install.sh` with a hash manifest that refuses to overwrite a hand patch and offers `--verify` as the daemon's start gate; one `owner-pause.sh` whose every phase is clamped to the briefed deadline and which releases queued dispatches through `watchdog/drain` rather than killing them; one `owner-resume.sh` that restores only from the recorded state and checks every precondition first; one `owner-say.sh` whose `terminal` mode writes `watchdog/goal-hold` before the message. Lesson: a script with no installer has no version, and a stop order needs a mechanism, not a convention.
- **The merge path was a /tmp script with timer-based failure markers (W5).** Symptom: ready PRs sat open; the daemon's `pr<N>.failed` markers were bare touch files with a two-hour backoff, so one systemic lane failure blocked every affected PR for two hours; PAR was a constant; three lane-runner revisions were hand-patched during the run; and the lane carried a fallback push with `MIPSTARRE_SKIP_HOOKS=1`. Diagnosis: a failure with no class can only be handled by a timer, and a timer cannot tell a conflict that is still there from one a merge of main already resolved. Fix: `merge-daemon.sh`, `merge.sh`, `daemon-scan.py`, `daemon.conf`, `lane.sh` and `worktree_resolve.sh` land in the repository; the marker becomes a JSON record with a class, a reason and an attempt count that clears on an observable change (a new head, a finished repair, a conflict that no longer reproduces, a newer installed release); PAR is computed from nproc, load and free slots each loop; and the hook-skipping fallback push is deleted. Lesson: a backoff is what you use when you have no observation - every marker should name the thing that would clear it.
- **The run's debris was cleared by hand, by date glob and by digit filter (W6).** Symptom: sessions killed by the provider were re-dispatched in hand-built waves; parked lanes were repaired by an operator reading `needs-attention` files; four PRs whose content was already on main stayed open; twenty stale lane directories were swept with globs that would have deleted live state on a different day. Diagnosis: nothing owned the state a failed run leaves behind, so the cleanup was improvised each time and the improvisation selected by filename rather than by record. Fix: `local/bin/janitor.sh` is one idempotent sweep of five passes selecting by record field only - re-dispatching a session that ended in a transient class under a per-(PR, role, head) budget and never one that ended clean, repairing `merge`/`build` lanes through committed briefs and `fix-lane.sh`, closing a PR only when its three-dot diff against main is empty AND its head is an ancestor of main, dropping lane state whose PR is closed, and expiring dispatch spool entries past the run's cutoff. Lesson: a cleanup that selects on a filename is a cleanup that will one day delete live work.
- **Two one-host fixes: the union driver and the import closure (W7).** Symptom: nearly every merge conflicted on the append-only telemetry logs until a union merge driver was written into one host's `.git/info/attributes`, where it protects exactly one checkout; and separately, two modules outside the umbrella import closure had no `.olean` after `lake build`, so every lane's per-file pre-push gate failed three hours into the run. Diagnosis: both fixes were correct and neither was committed, so neither existed for anyone else; and nothing checked reachability at the time a module was added, which is the only cheap moment to check it. Fix: a committed `.gitattributes` carries the union driver and `worktree-setup.sh` asserts it on every bootstrap; `scripts/check_umbrella_imports.py` runs inside the existing `local-ci/build` step, names each unreachable module with its exact import line and re-export file, and never edits a re-export file. Five older orphans found on the head this landed on keep the step `--warn-only` under issue 551. Lesson: a fix that lives in one host's git config is a fix the project does not have.
- **Three defects appeared only when the seven items were built as one tree (integration).** Symptom: with all seven items applied, seven `test_run_mode` cases and one `test_install_owner_tools` case failed, although each item's suite had passed on its own. Diagnosis: (1) `run_mode.render_shim` knew two rendering positions for the speed tier and the committed shim template that landed with it uses a third, its anchored `SPEED_ARGS=` line, so `set speed` would have rewritten the exec line instead and produced a shim `install.sh` had never released; (2) `run_mode.controller_path` resolved `capacity_controller.py` next to itself while the controller resolves its policy under `MIPSTARRE_REPO_ROOT`, so tool and data could come from two roots and every pause in a temporary root exited 3; (3) the crontab test asserted "no /tmp in the install path" as a proxy for "installed from a file under the cache root", which is false on a host whose TMPDIR is /tmp. Fix: `render_shim` rewrites the anchored `SPEED_ARGS=` line and its output is now byte-identical to `install.sh` in both directions, and `apply_speed` calls `install.sh --record codex` so the daemon's `--verify` start gate stays green after a speed change; `controller_path` resolves under `repo_root()`; the two test assertions now check the invariants themselves. Lesson: items with disjoint file sets still share contracts, and a contract that is only written in an integration note is a contract nothing tests.
- **A fourth integration defect: the pause/resume round trip reproduced the failure it was built to fix.** Symptom: with the capacity controller installed, a briefed 5/28/33 came back from `run_mode.py pause` and `resume` as 1/1/2, while the resume message announced "caps primary 5, second 28, max-codex 33". Each tool's own tests passed: `test_run_mode.py` runs against a stub repository root with no controller, and `test_capacity_state_roundtrip.py` exercises the controller alone. Diagnosis: `apply` wrote the cap files itself and never seeded the controller, so `pause` asked a controller with no state to save the caps, it saved zeros, and `resume` restored its floor of 1 per account; the resume message was built from what the command intended to write rather than from what it read back, so the wrong numbers were announced confidently - which is precisely the 2026-09-12 resume script's failure, rebuilt. Fix: `apply` now calls `capacity_controller.py init` (a failure is a loud warning, since the caps it wrote are still correct), `resume` refuses when a cap file disagrees with the cap it restored, and its message reports the files rather than the intent; `scripts/tests/test_run_mode_capacity_roundtrip.py` pins the round trip against a repository root that has the controller in it. Lesson: when two tools each own part of one record, the test that matters is the one that installs both - and a report built from intent instead of from observation is a lie waiting for a deadline.
