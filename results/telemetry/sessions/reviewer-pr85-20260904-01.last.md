## Review

F1 is merge-critical. Git documents that patch IDs ignore whitespace and line numbers. A direct check gave the same ID, `76b49c7c…`, for Python patches placing `run()` inside versus outside an `if`; two different binary payloads at the same path likewise shared `426a0417…`. Whitespace is semantic in repository languages, so this can green a materially changed patch. Compare or hash canonical full binary diff bytes instead.

F2 breaks the exact-head evidence model. Candidate extraction reads any `pr=\d+ head=<sha>` text but does not require the current PR number, `row.commit_id == sha`, the locally produced reviewer identity, a matching source status, or a valid ledger structure. Untrusted review text can therefore cause this script to mint a trusted `local-review/summary`. The carried body also embeds the new marker before `gh_common.post_review` prepends it again.

F3 bypasses established guard semantics because publication occurs before the bot gate, per-PR lock, fix-lock check, and `head_moved`, while the dry-run check is at line 1022. Consequently `--dry-run` can publish evidence, concurrent invocations can race the non-atomic review POST, and a moving or bot-authored head can bypass its prescribed skip.

F4 contradicts the stated “without a new reviewer round” behavior. Every carry creates another marker review, while `ROUND` counts all marker reviews. Repeated fresh-base merges can therefore force the next genuine review past the four-round cap and repeat the same ledger in prior context.

F5 leaves this gate-changing path untested. Existing coverage tests `gh_common.post_review`, not `review.sh`. Tests should cover exact versus whitespace/binary changes, malformed source evidence, clean/adverse carries, dry-run, guard ordering, concurrency/idempotence, and round counting.

`bash -n` and `git diff --check` passed. The workflow test suite could not run in this read-only sandbox because Python found no writable temporary directory; the supplied exact-head CI trigger reports success.
